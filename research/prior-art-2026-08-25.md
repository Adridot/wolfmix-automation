# Prior art survey — 2026-08-25

Scope: everything publicly reachable about controlling or decoding a Wolfmix
W1, checked on 2026-08-25. Goal: stop re-deriving what someone already
published, and find out how much of our work is actually unique.

Confidence vocabulary used below (external sources cannot be `device-confirmed`
by us, so a separate scale is used):

- **[src-doc]** — stated in a source we fetched ourselves; the fact is *that
  the source says it*, not that it is true of our hardware.
- **[src-tested]** — the source claims it observed the behaviour on real
  Wolfmix hardware.
- **[snippet]** — only reachable through a search-engine summary; the page
  itself refused automated fetch. Weakest tier, treat as a lead.
- **[ours-inferred]** — our reading of the source, not something it says.

`forum.wolfmix.com`, `qlcplus.org/forum` and some vendor pages sit behind a
Cloudflare bot challenge: direct fetch returned **HTTP 403 with a
"Just a moment..." interstitial**. The challenge was not bypassed, so every
forum fact below is tagged `[snippet]`.

## 1. mseerig/wolfmix-web-remote

Read: `README.md`, `IMPLEMENTATION.md`, `BUGLIST.md`, `FEATURELIST.md`,
`src/config.js`, `src/mapping.js`, `wiki/midi-mapping.md`, `wiki/osc-api.md`,
plus the full tree via
`https://api.github.com/repos/mseerig/wolfmix-web-remote/git/trees/main?recursive=1`
(38 files, last push 2026-02-19, 23 commits, default branch `main`).

### Transport — MIDI only, no protocol-level access **[src-doc]**

A Raspberry Pi 4 is put in USB gadget mode (`dwc2`, `libcomposite`,
`usb_f_midi` — `scripts/setup-midi-gadget.sh`, `scripts/midi-gadget.service`)
so the Pi's USB-C port presents itself to the W1 as a class-compliant USB MIDI
device. The Node server writes raw MIDI bytes straight to `/dev/snd/midiC*D*`
(`src/midi.js`). Browser ↔ server is Socket.IO on **port 3000**; OSC is
**UDP 8000 in / 9000 out** (`src/osc.js`).

**No WebSerial, no WebUSB, no protobuf, no `.wpj` reading or writing, no OS2L,
no knowledge of our 9-byte serial header.** Explicitly checked — the repo has
no `.proto`, no opcode constants, and nothing resembling `GET_PROJECT`.

### The default MIDI map **[src-doc]**

From `src/config.js` and `wiki/midi-mapping.md`:

| Surface | Channel | Number | Formula / range |
|---|---|---|---|
| Pads, pages 1–6 (20 per page) | 1 | note 0–119 | `note = (page-1)*20 + (button-1)` |
| Pads, pages 7–10 | 2 | note 0–79 | `note = (page-7)*20 + (button-1)` |
| Faders 1–8 = groups A–H | 1 | CC 1–8 | value 0–127, 0 = bottom |
| Fader 9 = Master | 1 | CC 9 | |
| Page switch, pages 1–10 | 4 | note 0–9 | `note = page-1` |
| Function buttons | 3 | note 0–6 | `bpm`=0, `wolf`=1, `blind`=2, `strobe`=3, `speed`=4, `blackout`=5, `smoke`=6 |

**Critical caveat, and the reason this is weaker than it looks:** the README
says these are the project's *own* defaults, which the user must mirror on the
device (`Settings → MIDI Mapping`). They were **not** read out of the firmware.
So this is *not* a factory MIDI map, and the function-button order
(`wolf, blind, strobe, speed, blackout, smoke`) is one author's choice — it
differs from the order of our `type 102 field 4` (`WOLF, STROBE, BLINDER,
SPEED, BLACKOUT, SMOKE`, device-confirmed in `wpj-format-registry.md`) and
therefore **corroborates nothing** about our byte indices.

What it does confirm structurally: **10 pages × 20 pads = 200**, 8 group faders
+ 1 master, 7 function controls. That matches the preset identity rule
(`id = (page-1)*20 + (slot-1)`) already documented by wpj-toolkit.

### Firmware behaviours the author says he measured **[src-tested]**

From `FEATURELIST.md` and `BUGLIST.md` — these are the genuinely new facts:

1. **The W1 is a MIDI sink only.** Quoted as "MIDI sink-only", with Rx bytes
   always 0 and no MIDI output over USB. Consequence: no feedback path, no
   button-state or colour readback over MIDI. Our `GET_SETTINGS` polling stays
   the only observability channel we have.
2. **A preset change resets the controller's internal button states.** If a
   flash function button is held (NoteOn outstanding) and autoplay advances to
   the next preset, the firmware releases it internally while the remote still
   believes it is held. Directly relevant to `SET_PRESET` (event 41) and
   `SKIP_PRESET` (43) automation, and to any flash-FX experiment that spans a
   preset change.
3. **Only one BPM input** is supported by the device.
4. MIDI Clock `0xF8` at 24 PPQN is accepted as a sync source.
5. On firmware 2.0, **page switching and live-effect editing over MIDI are not
   supported** — despite the project shipping a page-switch mapping on
   channel 4 (so that mapping is aspirational).

### OSC surface **[src-doc]** (`wiki/osc-api.md`)

`/pad/<page 1-10>/<button 1-20>` float 0.0/1.0 · `/fader/<1-8>` and
`/fader/master` float 0.0–1.0 · `/fn/<id>` float 0.0/1.0 with ids
`bpm|wolf|blind|strobe|speed|blackout|smoke` · `/bpm` float 20–300 plus
`/bpm/tap|start|stop|toggle`. TouchOSC-compatible. Of no direct use to us, but
it is the shape a future remote of ours would mirror.

`README.md` states MIT, but the repository tree contains **no `LICENSE` file**
and the GitHub API reports no detected licence. Fine to cite; do not vendor
code from it without asking the author.

## 3. OS2L — the endpoint is WTOOLS, and that is the interesting part

**[snippet]** (forum t=630, t=580; VirtualDJ forum 253475): the documented
setup is VirtualDJ `OS2LdirectIP = 127.0.0.1:9996`, and **WTOOLS** — not the
W1 — listens on that port (`WTOOLS → settings → OS2L port → 9996`, then
enable OS2L on the *My Wolf* tab). The W1 is connected to the host by USB
while this runs.

**[snippet]** The W1 honours **beat / BPM sync only**. VirtualDJ's
`os2l_button`, `os2l_cmd`, `os2l_info` and `os2l_scene` verbs are *not* acted
on by the controller.

**[ours-inferred]** Therefore the beat information has to reach the device
over the same USB serial link we already speak, and it must be an event id we
have not yet identified (our known set is 2–12, 16, 18–21, 39, 41, 43, 44).
`Settings` field 2 `extSyncState` is presumably the flag that gates it. This
is a cheap, concrete target: run WTOOLS with OS2L active and capture the
serial traffic.

## 4. Vendor position on remote control **[snippet]**

Forum t=736 (staff answer): the Wolfmix "has no communication protocols
embedded (beside MIDI)"; WTOOLS is the link between the device and the network
/ cloud, and **WTOOLS exposes no remote-control API**. The device accepts MIDI
(group/master dimmers via CC, preset selection via notes, MIDI clock) and
DMX-IN / **WLINK** for coarse per-channel manipulation.

Read together with §1 and the absence of any Companion module, this is the
clearest statement available that **the USB serial protobuf link is
undocumented by the vendor and unpublished by anyone else**.

**[snippet]** MIDI assignment on the device is done by learn:
`SHIFT + the corresponding encoder` puts a control into LEARN, then moving the
external fader / pressing the external button assigns it (forum t=688, t=747).
That screen is `WM_MODE_MAPPING = 43`, which `research/mode-map.md` already
records as reachable on our MK1.

## 5. Easy View / MEVP / 3D link — nothing usable found

**[src-doc]** The legacy visualiser link is **MEVP** ("Magic 3D Easy View
Protocol"), implemented as a Windows DLL, `MEVP.dll`, loaded in-process by the
controlling application (DMXControl wiki page above). QLC+ declined to support
it — "runs only on Windows and it's close source" — and uses **ArtNet**
instead (SourceForge thread 8fc1e786).

**[src-doc]** Vendor material lists Easy View's network inputs as ArtNet,
Sandnet, ACDI and MEVP, up to 4 universes / 2048 channels.

**Nothing public documents the modern WTOOLS → Easy View link, the UDP port
3024 we sniffed on loopback, its frame format or its XOR, and nothing
mentions a DTLS proxy or patch conversion for it.** Our
`wolfmix-dmx-observability` note remains the only description of it. The one
practical spin-off: Easy View also ingests **ArtNet**, so if we ever want a
visualiser fed by *our* data we do not have to reproduce the 3024 frames.

## 6. "wolfmix_project_v2" — the name does not exist **[snippet]**

No public reference to a `wolfmix_project_v2` container. The only "v2" in the
Wolfmix world is cosmetic: converting a pre-2.0 project in WTOOLS appends a
**`v2` suffix to the project *name*** so 2.0-native projects are not confused
with, or backed up over, their 1.x originals. There is also an unrelated
`.ev2` file (an Easy View 2 scene that can accompany a `.wpj`). **Do not spend
time looking for a v2 container format.**

## 7. Two structural numbers worth cross-checking **[snippet] / [ours-inferred]**

Vendor/support material states the W1 has **100 regular presets plus 40 Live
Edit presets**, and the hardware is a **4-universe / 2048-channel** device.

Our variant-C top-level protobuf (`wpj-format-registry.md`) has field 3
repeated **100** times (presets — matches) and field 15 repeated **2048**
times (currently "unknown, large volume"). 2048 = 4 × 512 = the full channel
count, so **field 15 is most likely one entry per DMX channel**, not steps or
sequences. That is a testable prediction, not a finding.

## What this changes for us

Concrete next steps, cheapest first:

1. **Look for the MIDI-mapping record in the `.wpj`.** The map is per-project
   state edited on the device (`WM_MODE_MAPPING = 43`, learn = SHIFT +
   encoder). A full map is ~216 assignments (200 pads + 9 faders + 7 fn).
   Experiment **MAP-01**: on `WMX EXP format-lab`, learn exactly one pad to
   one MIDI note, save, diff records. Prime suspects among our still
   unattributed TLV types: 110, 111, 116, 120, 125, 130, 151, 161.
2. **Find the OS2L / beat-sync event id.** Run WTOOLS with OS2L enabled on
   9996 and capture the USB serial traffic; the tempo path must be an event
   outside our known set. Do this when the port is free — it needs a sniffer,
   not our client.
3. **Do not chase a "v2" container**, and do not chase MEVP: both are dead
   ends (§5, §6).
4. **Re-read field 15 as per-channel data** (2048 = 4 × 512) before assuming
   it is sequencer content.
5. **Flash/preset interaction caveat for future experiments**: a preset change
   resets the controller's internal button states, so never hold a flash key
   across a `SET_PRESET` / `SKIP_PRESET` and expect it to survive.
6. Treat the mseerig default MIDI map as *his* defaults, not the firmware's.
   Do not use its function-button order as evidence for anything.

What this survey does **not** answer — all still open, all still ours to do:

- **The serial protocol.** No public `.proto`, no event/opcode list, no
  message schema, no header description. Our 9-byte header and events
  2–12/16/18–21/39/41/43/44 have zero external corroboration.
- **TLV semantics.** Nothing new on types 102, 105, 106, 110, 111, 115, 116,
  120, 125, 130, 140×8, 145×8, 150×8, 151, 155, 160, 161 beyond what
  wpj-toolkit already gave us (101, 135, 165).
- **Variants B and C.** No source anywhere describes a `.wpj` that is bare
  protobuf without the TLV container, and nothing explains the top-level
  version field `6` vs `7`.
- **`.wm` / `.wmx`.** No public word on the encryption, on the 32-hex and
  64-hex segments, or on how the fixture profiles are packed.
- **The 3D link.** UDP 3024 frame layout, its XOR, the DTLS proxy and any
  patch conversion remain undocumented outside our own notes.
- **MK1 vs MK2 differences** in the file format. wpj-toolkit documents MK2
  files and does not state firmware coverage; nobody else addresses it.
- **The rig-c blackout bug.** Nothing beyond
  `research/forum-findings-2026-08-25.md`.
